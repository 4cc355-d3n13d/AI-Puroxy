# Архитектура

> Документация репозитория. Не путать с `app/docs/` — там лежат исходные `.md`
> документации ИИ-API, которые сервис отдаёт на маршруте `/docs`.

## Общая схема

```
клиент ──► http://localhost:8787/v1/...
              │
              ├─ подставляет Authorization: Bearer <api_key>
              ├─ проксирует на base_url/v1/... (httpx, стриминг сквозной)
              ├─ разбирает usage/стоимость, пишет запрос и ответ в DuckDB
              └─ при низком балансе дописывает предупреждение в текстовый ответ
              │
              ▼
        data/proxy.duckdb ──► /_api/* ──► /monitor /balance /models
```

Один процесс: FastAPI + uvicorn. Внешних сервисов, брокеров и CDN нет —
JS и CSS отдаются с диска, графики рисуются инлайновым SVG.

Слушает `127.0.0.1`, если не задан `AI_PROXY_HOST`. Аутентификации у интерфейса нет
и не планировалось: сервис проектировался как локальный инструмент, а на `/settings`
открыт API-ключ. Открытие наружу — осознанное решение пользователя.

## Модули

| Файл            | Ответственность                                                                 |
| --------------- | ------------------------------------------------------------------------------- |
| `app/main.py`   | Маршруты: HTML-страницы, `/_api/*` для интерфейса, сквозной прокси, фоновая задача |
| `app/proxy.py`  | Проксирование, стриминг SSE, кэш баланса, вставка предупреждения                  |
| `app/db.py`     | DuckDB: схема, запись лога, снимки баланса, кэш цен, ретеншен                     |
| `app/usage.py`  | Разбор `usage`/стоимости/баланса, оценка цены по прайсу                           |
| `app/stats.py`  | SQL-агрегаты для интерфейса                                                      |
| `app/config.py` | Конфигурация в `data/config.json`, приведение типов                              |
| `app/docsrc.py` | Чтение `.md`, замена домена, рендер в HTML, оглавление                            |
| `app/inspect.py`| Разбор тел: диалог, рассуждения, вызовы инструментов, токены, картинки            |
| `app/media.py`  | Медиа из тел: base64 → файлы в `data/media/`, учёт ссылок для галереи             |
| `app/__main__.py`| Запуск `python -m app` с адресом и портом из настроек                           |

Зависимости между модулями односторонние: `main → {proxy, stats, docsrc, config, db, media}`,
`proxy → {config, db, media, usage}`, `stats → {db, inspect}`, `usage → db`,
`db → {config, inspect, media}`, `inspect → media`, `media → config`. Циклов нет.

## Путь запроса через прокси

`app/proxy.py:handle()`:

1. **Проверка конфигурации.** Без `api_key`/`base_url` — сразу `503` с телом
   `{"error": {"type": "proxy_not_configured"}}` и подсказкой про `/settings`.
2. **Разбор входящего запроса.** Тело читается целиком, из него достаётся `model`
   и флаг `stream`. Путь нормализуется в ярлык эндпоинта (`_endpoint_label`).
3. **Заголовки.** Вырезаются `host, authorization, content-length, connection,
   accept-encoding, transfer-encoding, expect, cookie, x-api-key`; подставляется свой
   `Authorization`. `accept-encoding` убирается намеренно: httpx распаковывает ответ,
   и исходный заголовок сделал бы тело нечитаемым.
4. **Отправка.** `client.send(..., stream=True)` — решение о буферизации принимается
   уже по `Content-Type` ответа. Таймауты: connect 15 с, read 900 с, write 120 с.
   Сетевая ошибка → `502` и запись в лог с `error`.
5. **Ветвление по типу ответа.**
   * `text/event-stream` → `StreamingResponse` с генератором `_stream_response`.
   * Иначе тело читается целиком, разбирается и логируется.
6. **Медиа.** До отправки из тела запроса (копии, не того, что уходит в апстрим)
   вынимаются встроенные картинки — см. «Медиа» ниже; то же делается с телом ответа.
   Найденное прикладывается к записи как `entry["media"]`.
7. **Побочные эффекты** (`_post_process`): ответ `GET /v1/models` обновляет кэш цен
   источника (и досчитывает оценки прошлым запросам этих моделей),
   ответ `GET /v1/balance` — снимок баланса. Стоимость запроса вычитается из кэша
   баланса, чтобы предупреждение не отставало от реальности между опросами.
8. **Вставка предупреждения** — только при статусе < 400 и только в текстовые ответы.
9. **Запись в лог** и возврат ответа клиенту.

Из ответа вырезаются `content-length, content-encoding, transfer-encoding, connection,
keep-alive, server, date` — остальные заголовки апстрима идут клиенту как есть.

### Важная деталь логирования

В лог пишется **оригинальный ответ апстрима**, без вставленного предупреждения:
`entry["response_body"]` заполняется до модификации тела. Так лог остаётся честным
слепком того, что вернул API. Единственное отличие — встроенные base64-данные заменены
ссылкой `media://<файл>` на сохранённый файл.

## Стриминг

`_stream_response` — асинхронный генератор, который режет входящий поток по `\n\n`
и переотправляет события **дословно**, не пересобирая их из разобранного JSON.
Попутно из `data:`-строк собираются:

* итоговый `usage` (последнее непустое значение по чанкам, `merge_stream_usage`);
* текст ответа — чтобы в интерфейсе был читаемый результат, а не сырые события;
* `model` и `id`, если их не было в запросе.

Клиент не ждёт завершения: события уходят по мере поступления. Запись в лог
происходит в `finally`, то есть даже при обрыве соединения с апстримом.

`\r\n` нормализуются в `\n` при разборе границ событий.

### Вставка предупреждения в поток

| Эндпоинт             | Как вставляется                                                              |
| -------------------- | ---------------------------------------------------------------------------- |
| `chat/completions`   | Дополнительный первый чанк `chat.completion.chunk` с `delta.content`, собранный по `id`/`model`/`created` первого реального чанка |
| `messages`           | Событие `content_block_delta` с `text_delta`, отправленное сразу после первого `content_block_start` текстового блока |

Оба варианта протокольно корректны, поэтому клиентские SDK разбирают их штатно.

## Хранилище

DuckDB, один файл `data/proxy.duckdb`, одно соединение на процесс под `threading.RLock`
(DuckDB не допускает нескольких писателей в файл).

```sql
requests(
  id BIGINT PK DEFAULT nextval('seq_request_id'),
  ts TIMESTAMP, day DATE,
  method, path, endpoint, model, stream BOOLEAN,
  status_code INTEGER, duration_ms DOUBLE, client_ip, upstream_id,
  request_body VARCHAR, response_body VARCHAR, error VARCHAR,
  prompt_tokens BIGINT, completion_tokens BIGINT, total_tokens BIGINT,
  cost DOUBLE, cost_source VARCHAR      -- 'api' | 'estimated' | NULL
)
balance_snapshots(ts TIMESTAMP, day DATE, amount DOUBLE, source VARCHAR)
model_prices(upstream, model, cost_context, cost_completion, currency, updated_at,
             PRIMARY KEY (upstream, model))
media(key PK, direction, kind, file, url, mime, bytes, model, upstream, prompt,
      request_id, ts, day, last_request_id, last_ts, last_day, uses)
```

Добавлены позже через `ALTER TABLE`: у `requests` — `upstream`, `cost_api`, `cost_estimated`,
`media_out`, `media_scanned`; у `balance_snapshots` — `upstream`. Старая `model_pricing`
(ключ — только модель) осталась ради миграции: `db.migrate` переносит её строки
в `model_prices` под первый источник и очищает.

* `day` дублирует дату из `ts` — по нему идут все группировки и ретеншен.
* `endpoint` — нормализованный путь (`v1/async/media/tasks/{task_id}`), чтобы
  задачи не расползались на тысячи уникальных значений в фильтрах и статистике.
* Тела запроса и ответа обрезаются до 400 000 символов с пометкой об обрезке.
* Для стрима в `response_body` кладётся JSON `{stream, text, events, raw}`,
  где `raw` — последние 200 событий.

**Поля разбора.** `prompt_preview`, `answer_preview`, `reasoning_preview`, `tools_offered`,
`tools_called`, `images`, `finish_reason`, `reasoning_tokens`, `cached_tokens` заполняет
`inspect.compact` при записи — чтобы список лога не парсил JSON на каждую строку.
Колонки добавляются через `ALTER TABLE … ADD COLUMN IF NOT EXISTS`, поэтому существующие
базы не нужно пересоздавать; старые записи разбирает `backfill_details()` при старте
(признак — колонка `inspected`). Карточка запроса, наоборот, разбирает тела на лету
(`inspect.summarize`): так она работает и для записей, сделанных до появления полей,
и не дублирует текст в базе.

**Ретеншен.** `apply_retention(n)` удаляет из `requests` и `balance_snapshots` записи
с `day < сегодня - n`, из `media` — строки с `last_day` старше границы, и файлы, на которые
больше не ссылается ни одна строка. При `n = 0` не делает ничего. Вызывается при старте,
при сохранении настроек и в фоновом цикле.

**Миграция при старте** (все шаги идемпотентны): `migrate` проставляет старым записям
и снимкам первый источник, переносит прайс и раскладывает `cost` в `cost_api` /
`cost_estimated`; `backfill_details` и `backfill_media` разбирают тела записей,
сделанных до появления полей; `recompute_costs` применяет текущий режим стоимости.

## Источники

`config.sources` — список `{id, name, base_url, api_key}`, `active_source` — id активного.
`config.load()` добавляет производные `api_key`, `base_url` и `source` от активного,
поэтому прокси и фоновый опрос баланса работают с ними как с одиночными полями.
`id` — ключ истории в базе (`requests.upstream`, `balance_snapshots.upstream`,
`model_prices.upstream`): строится по хосту base URL и при переименовании не меняется.
Кэш баланса в `proxy` помнит, к какому источнику относится, и после переключения
считается неизвестным.

## Стоимость

У каждой записи две суммы: `cost_api` (из `usage` ответа) и `cost_estimated` (по прайсу
источника). `cost`/`cost_source` — выбранная по `config.cost_mode`; все агрегаты читают
только их. Смена режима — один `UPDATE` (`db.recompute_costs`) без разбора тел.

## Медиа

`media.extract_request` обходит JSON запроса: строки `data:…;base64,…`, блоки
`{"type": "base64", "data": …}` и поля `b64_json` декодируются и сохраняются в
`data/media/<sha256[:32]>.<ext>`, а в копии тела заменяются на `media://<файл>`. Ссылки
`http(s)` собираются только под ключами, в имени которых есть `image` (`image_url`,
`image_urls`, `reference_image_urls`…), — иначе в галерею попадали бы любые URL.
`media.extract_response` ищет результаты только в известных местах (`resultUrls`,
`data[]` у images/generations, `message.images`): ответ статуса задачи повторяет входные
параметры, и обход по ключам записал бы вход в результаты.

В таблице `media` одна строка на уникальную пару «направление + файл/URL»; повторная
встреча сдвигает `last_*` и увеличивает `uses`. Карточка запроса картинки из таблицы
не берёт — `inspect.summarize` находит их в теле и превращает `media://` в `/_media/<файл>`.

## Баланс

Три источника, дополняющие друг друга:

1. **Фоновый опрос** `/v1/balance` раз в `balance_poll_seconds` (по умолчанию 300 с) —
   пишет снимок в `balance_snapshots`.
2. **Проксированный запрос** клиента к `/v1/balance` — тоже даёт снимок, бесплатно.
3. **Локальная коррекция**: после каждого запроса со стоимостью кэш в памяти
   уменьшается на эту сумму. Нужна, чтобы порог предупреждения срабатывал вовремя,
   а не через пять минут.

Кэш живёт в модуле `proxy` (`_balance_amount`, `_balance_checked_at`), защищён
`asyncio.Lock`. Снимки же позволяют показать в интерфейсе фактическое изменение
баланса за день — это единственный способ увидеть траты, которые API не тарифицирует
в ответе (медиа-задачи), и пополнения счёта.

## Конфигурация

`data/config.json`, кэшируется в памяти, пишется атомарно (через `.tmp` + `replace`).
Значения приводятся к типам по образцу `DEFAULTS`, десятичная запятая допускается.
Первичные значения можно задать через `AI_PROXY_API_KEY` и `AI_PROXY_BASE_URL`,
каталог данных — через `AI_PROXY_DATA_DIR` (используется в тестах).

Ключ хранится открытым текстом — `data/` в `.gitignore`.

## Документация на `/docs`

`app/docs/*.md` читаются с диска и кэшируются (`lru_cache`, сбрасывается при сохранении
настроек). Конвейер обработки:

1. **Служебная шапка** со ссылкой на индекс документации вырезается.
2. **MDX-компоненты разворачиваются** в обычный markdown (`_demdx`): исходники написаны
   для MDX, и без этого `<Note>`, `<Card>`, `<CardGroup>`, `<CodeGroup>` выводились бы
   на страницу как текст. `<Card>` становится пунктом списка со ссылкой,
   `<Note>`/`<Tip>`/`<Warning>` — цитатой с подписью, обёртки просто снимаются.
3. **Перекрёстные ссылки** вида `/docs/api-reference/media/image-models` переписываются
   на локальные (`_relink`), иначе они вели бы на внешний сайт.
4. **Домен** `speshu.ai` заменяется на значение из настроек: для локальных доменов
   схема понижается до `http`, для остальных остаётся `https`.
5. **Рендер** через `markdown-it-py` с таблицами; заголовкам `h2`/`h3` проставляются
   якоря, из них же строится оглавление справа.

Порядок и группировка страниц заданы в `docsrc.SECTIONS` как пары «slug — ярлык
эндпоинта». Ярлык показывается бейджем над заголовком; у страниц-каталогов
(модели изображений, видео, аудио) он пустой, потому что отдельного эндпоинта у них нет.
Сопоставление slug с исходным путём документации живёт в `_original_path`.

## Фронтенд

Серверный рендер страницы (Jinja2) + подгрузка данных через `/_api/*`.
Общий слой — `static/common.js`: форматирование чисел и денег, экранирование,
палитра и рисование линейного графика инлайновым SVG — по линии на модель,
с сеткой, «круглой» верхней границей шкалы (`niceMax`), направляющей и подсказкой
по наведению на день.

Цвет модели назначается по её позиции в легенде, а не хэшем от имени: моделей
на графике не больше девяти (топ-8 плюс «прочие»), поэтому коллизий не бывает.
Первая версия считала цвет хэшем ради устойчивости между перерисовками — на линейном
графике две модели получили одинаковый оттенок, и это оказалось важнее устойчивости.

Тема — CSS-переменные: светлая палитра на `:root`, тёмная — под `prefers-color-scheme`
(если не выбрана светлая явно) и под `:root[data-theme="dark"]`. Кнопка в шапке
перебирает «как в системе → светлая → тёмная» и хранит выбор в `localStorage`;
inline-скрипт в `<head>` ставит `data-theme` до загрузки CSS, чтобы тёмная страница
не мелькала светлой. `color-scheme` задан в обеих палитрах — иначе поля дат,
выпадающие списки и полосы прокрутки оставались бы светлыми.

**Автообновление лога** (`monitor.js`, `patchLog`) сопоставляет строки по `id`:
существующие узлы и раскрытая под строкой карточка не пересоздаются, новые вставляются
на свои места, а позиция открытой (или первой видимой) строки на экране сохраняется
компенсацией прокрутки. Если открытая запись уходит со страницы, таблица не трогается —
вместо этого показывается «+N новых».

**Просмотр медиа** — общий для лога и галереи (`common.js`: `mediaThumb`, лайтбокс).
Миниатюры с одинаковым `data-group` листаются стрелками.

## Запуск и перезапуск

`python -m app` читает адрес и порт из настроек и выставляет `AI_PROXY_LISTEN`, по которому
`/settings` сравнивает фактический адрес с сохранённым. Описание сервиса (plist/юнит)
адреса не содержит и выставляет `AI_PROXY_SERVICE=1`: только тогда `POST /_api/restart`
завершает процесс сигналом `SIGTERM`, а launchd (`KeepAlive`) или systemd (`Restart=always`)
поднимают его уже на новом адресе. Без сервиса перезапуск вернул бы просто остановку,
поэтому он запрещён (`409`).
