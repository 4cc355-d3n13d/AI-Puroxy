# Заметки по ИИ-API (SpeShu.AI)

Что выяснилось при проверке живого API 2026-08-15. **Документация местами расходится
с реальностью** — код поддерживает оба варианта, чтобы не сломаться при выравнивании.

## Базовый URL и авторизация

* Сервер: `https://speshu.ai/api`, пути добавляются как `/v1/…`.
* Ключ: `Authorization: Bearer <ключ>`.

## Расхождения документации и живого API

### 1. Формат баланса

| Источник      | Ответ `GET /v1/balance`      |
| ------------- | ---------------------------- |
| Документация  | `{"amount": "9.28591714"}`   |
| Живой API     | `{"RUB": "1851.736450999998"}` |

`usage.parse_balance` перебирает ключи `amount`, `RUB`, `rub`, `balance`, `value`
и заглядывает во вложенный `data`.

Страница `/docs/balance` намеренно отличается от исходника: в ней описан **реальный**
ответ `{"RUB": …}`, а примеры на Python и JavaScript читают `data['RUB']`.
Это единственное место, где локальная документация правит содержимое, а не только домен —
копия исходника здесь вводила бы в заблуждение.

### 2. Формат стоимости в `chat/completions`

| Источник      | Поле                                            |
| ------------- | ----------------------------------------------- |
| Документация  | `usage.cost_rub` и `usage.cost` (числа)         |
| Живой API     | `usage.cost.total_cost` (вложенный объект)      |

`usage.extract_cost` проверяет `usage.cost.{total_cost,total,cost_rub,amount,rub}`,
затем `usage.{cost_rub,cost,total_cost,total_cost_rub}`.

Живой ответ:

```json
{"usage": {"prompt_tokens": 19, "completion_tokens": 6, "total_tokens": 25,
           "prompt_tokens_details": {"cached_tokens": 0, "cache_write_tokens": 0},
           "completion_tokens_details": {"image_tokens": 0},
           "cost": {"total_cost": 0.000174}}}
```

### 3. `/v1/messages` не возвращает стоимость вообще

Ответ в формате Anthropic, `usage` есть, поля стоимости нет:

```json
{"usage": {"input_tokens": 19, "output_tokens": 6,
           "cache_creation_input_tokens": 0, "cache_read_input_tokens": 0,
           "service_tier": "standard"}}
```

Поэтому для этого эндпоинта стоимость **оценивается по прайсу** и помечается
`cost_source = 'estimated'` (в интерфейсе — звёздочка и подпись «оценка»).
Токены приводятся к общей схеме: `prompt_tokens = input_tokens + cache_read + cache_creation`.

### 4. Каталог моделей проще, чем в OpenAPI-схеме

Документация описывает `pricing`, `providers`, `supported_parameters`.
Живой `GET /v1/models` (67 моделей) отдаёт плоскую структуру:

```json
{"id": "anthropic/claude-fable-5", "object": "model", "created": 1781070651,
 "owned_by": "anthropic", "title": "Claude Fable 5", "context_length": 1000000,
 "cost_context": "1374.45", "cost_completion": "6872.25", "currency": "RUB"}
```

`cost_context` / `cost_completion` — рубли за 1M токенов. `db.upsert_model_pricing`
читает и плоский формат, и вложенный `pricing.{prompt,completion}` из документации.

### 5. Каталог моделей провайдер-специфичен

`openai/gpt-4o-mini` → `404 model_not_found`. Названия моделей нельзя переносить
из чужих примеров, надо брать из `GET /v1/models`.

Самые дешёвые на момент проверки (₽ за 1M, контекст/ответ):

| Модель                      | Контекст | Ответ  |
| --------------------------- | -------- | ------ |
| `google/gemma-3n-e4b-it`    | 3.74     | 7.48   |
| `openai/gpt-oss-20b`        | 5.61     | 20.57  |
| `qwen/qwen3.7-flash`        | 7.15     | 30.99  |
| `nvidia/nemotron-3.5-lightning` | 8.74 | 34.97  |

## Точность оценки по прайсу

Оценка **приблизительная**. Замер на `google/gemma-3n-e4b-it`, 18 промпт-токенов
и 5 токенов ответа:

* по прайсу: `18/1e6 × 3.74 + 5/1e6 × 7.48` = **0.000105 ₽**
* фактически из ответа API: **0.000157 ₽**

Расхождение ~1.5×: в каталожную цену, судя по всему, не входят все надбавки.
Поэтому оценка используется только как запасной вариант, всегда помечается в интерфейсе,
а для сверки на странице `/balance` показывается фактическое изменение баланса за день.

Проверка на реальном дне: 22 запроса, **0.003723 ₽ по логу** против
**0.003800 ₽ по дельте баланса** — разница как раз на оценённых запросах `/v1/messages`.

## Проверенные эндпоинты

Все девять из документации проксируются; в скобках — как эндпоинт пишется в лог.

| Метод | Путь                              | Проверка                                                    |
| ----- | --------------------------------- | ----------------------------------------------------------- |
| GET   | `/v1/models`                      | 200, 67 моделей, обновляет кэш цен                           |
| POST  | `/v1/chat/completions`            | 200, обычный и `stream: true` (SSE)                          |
| POST  | `/v1/messages`                    | 200, формат Anthropic, стоимость оценивается                 |
| GET   | `/v1/media/models`                | 200, ~135 КБ каталога                                        |
| POST  | `/v1/async/media/tasks`           | сквозной проксинг (платная генерация не запускалась)         |
| GET   | `/v1/async/media/tasks`           | 200, список задач с пагинацией                               |
| GET   | `/v1/async/media/tasks/{task_id}` | 404 на несуществующий id (`{"code":404,"msg":"not found"}`)  |
| POST  | `/v1/media/sessions`              | **201** (не 200, как в документации), `data.sessionId`       |
| GET   | `/v1/balance`                     | 200, формат `{"RUB": …}`                                     |

Маршрут в прокси сквозной (`/v1/{path:path}`), поэтому новые эндпоинты API
заработают без правок кода — просто попадут в лог с собственным ярлыком.

## Прочие наблюдения

* **Ошибки** отдаются в двух стилях: OpenAI-подобный `{"error": {"message", "type", "code"}}`
  у текстовых эндпоинтов и `{"code": 404, "msg": "not found"}` у медиа.
  `proxy._error_text` разбирает оба.
* **Медиа-прайс не потокенный**: тарификация по `unit_key` (например, `duration`)
  с тирами по разрешению и отдельными `conditional_rates`. Пересчитать стоимость
  задачи по каталогу нельзя без знания фактических параметров результата, поэтому
  медиа-траты в сумму по логу не попадают — только в дельту баланса.
* **Стриминг** отдаёт `usage` в предпоследнем чанке, перед `data: [DONE]`.
* Поле `id` ответа (`gen-…`) сохраняется в `upstream_id` — по нему удобно искать
  запрос в логе и сверяться с поставщиком.
