# Разработка и сопровождение

## Локальный запуск

```bash
./service.sh install            # обычный способ: сервисом (см. DOCS.md)
./run.sh                        # в переднем плане, адрес и порт из настроек
./run.sh 9000                   # разово другой порт
./run.sh 8787 --reload          # аргументы после порта уходят в uvicorn
AI_PROXY_HOST=0.0.0.0 ./run.sh  # разово доступ из локальной сети
./.venv/bin/python -m app       # то, что запускает сервис
```

Адрес прослушивания по умолчанию — `127.0.0.1`: у интерфейса нет аутентификации,
а API-ключ виден на `/settings`, поэтому наружу сервис открывается только явно.

Зависимости: FastAPI, uvicorn, httpx, DuckDB, Jinja2, markdown-it-py. Всё из PyPI,
внешних сервисов нет.

## Скрипты

| Скрипт        | Назначение                                                   |
| ------------- | ------------------------------------------------------------ |
| `install.sh`  | Создаёт `.venv` и ставит зависимости                          |
| `reset.sh`    | Удаляет `.venv`                                              |
| `run.sh`      | Запуск в переднем плане                                      |
| `run-all.sh`  | То же, но с `AI_PROXY_HOST=0.0.0.0`                          |
| `run-bg.sh`   | Черновой запуск в фоне                                       |
| `service.sh`  | Установка и управление сервисом (launchd / systemd)           |

`service.sh` запускает `python -m app` напрямую из `.venv`, а не через `run.sh`: у сервиса
не должно быть интерактивного вывода, а `KeepAlive` проще отслеживает один процесс.
Адрес и порт в описание сервиса не пишутся — `python -m app` читает их из
`data/config.json` при каждом старте, поэтому смена порта на `/settings` применяется
перезапуском. `run.sh` оставлен на `uvicorn` ради произвольных аргументов разработки.
Перед установкой скрипт проверяет, не занят ли порт посторонним процессом, —
иначе launchd попал бы в цикл перезапусков.

При правке кода сервис нужно перезапускать: `./service.sh restart`
(с `--reload` он не запускается — это режим разработки, не сервиса).

### Различия платформ

| | macOS (launchd) | Linux (systemd --user) |
| --- | --- | --- |
| Описание | `~/Library/LaunchAgents/com.aipuroxy.proxy.plist` | `~/.config/systemd/user/ai-puroxy.service` |
| Журнал | файлы `data/logs/service*.log` | journald (`journalctl --user -u`) |
| Автозапуск | при входе в систему | при входе; без входа нужен `loginctl enable-linger $USER` |

`data/logs/` на Linux **не заполняется** — если файлы там есть, они остались от другой
машины и показывают чужую историю. Поэтому `logs` и диагностика при сбое разведены
по платформам; общий код (`load_service`, `unload_service`) тоже обязан ветвиться,
иначе на Linux вызовется несуществующий `launchctl` и остановка молча не сработает.

### Грабли, на которых скрипт уже обжёгся

* **Команды должны знать фактический порт.** Раньше `restart` у сервиса на порту 9090
  проверял порт по умолчанию 8787, не получал ответа и рапортовал «Сервис не запустился»
  при живом и здоровом процессе. Теперь `read_address` берёт адрес из настроек, а у сервиса
  старого формата (адрес зашит в plist/юнит) — из его описания.
* **Перенос адреса из старого описания — только при `install`.** Если записать его
  в `config.json` при `status`, ещё работающий процесс прежней версии при сохранении
  настроек перезапишет файл без `host`/`port`, и после обновления сервис молча
  окажется на `127.0.0.1`.
* **`bootout` асинхронный.** Сразу после него метка ещё зарегистрирована, и следующий
  `bootstrap` падает с `Load failed: 5: Input/output error`. Поэтому есть
  `wait_until_unloaded`, который дожидается реального снятия.
* **Ошибки launchctl нельзя глушить.** Раньше стояло `bootstrap … 2>/dev/null || load -w`,
  и настоящая причина сбоя терялась. Теперь вывод показывается (`load_service`).
* **HTTP-ответ не значит «запустилось».** Умирающий прежний экземпляр успевает ответить
  200, и установка рапортовала успех, хотя сервис через секунду исчезал. `wait_until_up`
  проверяет ещё и живой PID (`launchctl list` / `MainPID`).
* **`lsof` есть не везде.** `port_holder` пробует `lsof`, затем `ss`, затем `fuser`:
  на Linux `lsof` часто не установлен, и проверка занятости порта тихо вырождалась
  в «свободен».
* **`.venv` может быть чужим.** `ensure_venv` не довольствуется наличием
  `.venv/bin/python`, а запускает его с импортом зависимостей: окружение, скопированное
  между машинами или ОС, проверку на исполняемость проходит, но падает при старте.

## Тесты

```bash
./.venv/bin/python tests/test_core.py   # логика: usage, баланс, ретеншен, документация
./.venv/bin/python tests/test_web.py    # HTTP: страницы, /docs, /_api/*
```

`test_core.py` — 85 проверок. Поднимает временный каталог данных через `AI_PROXY_DATA_DIR`
и проверяет разбор обоих форматов `usage` и баланса, оценку стоимости по прайсу, ретеншен,
замену домена в документации, вставку предупреждения, нормализацию путей, приведение
типов в конфигурации, а также разбор диалога/рассуждений/инструментов (`inspect`)
и склейку стрима (`proxy._StreamAccumulator`). Отдельно — источники (миграция старой
конфигурации, id, активный), режимы стоимости и пересчёт истории, миграция старых записей,
извлечение медиа из всех форматов, галерея, ретеншен файлов и `backfill_media`.

`test_web.py` — 40 проверок. Поднимает приложение через `TestClient` и дёргает каждую
страницу, каждую страницу `/docs` и все `/_api/*`; проверяет форму источников,
предупреждение о перезапуске, `409` у `/_api/restart` без сервиса и защиту `/_media/`. `DeprecationWarning` там возведён
в ошибку — без этого устаревшие вызовы живут незамеченными, пока библиотека их терпит,
и ломаются на машине с более свежими зависимостями.

Оба теста писались не для галочки и поймали реальные баги:

* `config` не принимал десятичную запятую при сохранении не через форму, и порог баланса
  молча падал в `0`.
* `templates.TemplateResponse("name", context)` (старая сигнатура) работал на Python 3.9
  со Starlette 0.49, но на Python 3.12 со Starlette 1.6 превращался в
  `TypeError: unhashable type: 'dict'` на **каждой** странице. Правильная форма —
  `TemplateResponse(request, "name", context)`, поддерживается с 0.29.

Внешняя сеть не требуется — тесты работают на временной базе.

Что тестами **не покрыто** (проверялось вручную на живом API): сетевой слой,
стриминг SSE, реальные запросы к апстриму.

## Типовые доработки

**Новый эндпоинт апстрима** — ничего делать не нужно, маршрут сквозной. Если для него
нужен особый разбор стоимости или побочный эффект, дописывается ветка
в `proxy._post_process` и, при необходимости, в `usage.extract_usage`.

**Новая страница документации** — положить `.md` в `app/docs/` и добавить в
`docsrc.SECTIONS` пару «slug — ярлык эндпоинта» (пустой ярлык скрывает бейдж).
Заголовок и подзаголовок берутся из первых `# ` и `> ` строк. Если slug не совпадает
с исходным путём документации, добавьте его в `_ORIGINAL_PATH_OVERRIDES`, иначе
перекрёстные ссылки с других страниц останутся внешними.

**Новый агрегат для интерфейса** — функция в `stats.py` + маршрут `/_api/…` в `main.py`.
Ответы прогоняются через `stats.jsonable`, иначе `datetime`/`date` не сериализуются.

**Новое поле в логе** — колонка в `db.SCHEMA` (через `ALTER TABLE … ADD COLUMN IF NOT EXISTS`,
он безопасен при повторном запуске) и в `INSERT` внутри `db.log_request`. Если поле
выводится из тел запроса/ответа, считайте его в `inspect.compact` и добавьте в
`backfill_details`, чтобы заполнить уже накопленные записи.

**Новый признак в карточке запроса** — `inspect.summarize` разбирает тела на лету,
поэтому достаточно дополнить его и отрисовку в `dialogView` (`static/monitor.js`).

## Что важно не сломать

* **DuckDB — один писатель.** Все обращения идут через единственное соединение под
  `threading.RLock` в `db.py`. Второй процесс на том же файле открыть не получится:
  сначала остановите сервер, потом читайте базу CLI-клиентом.
  Попытка запустить второй экземпляр даёт `db.DatabaseBusyError` с инструкцией вместо
  трейсбека DuckDB; `run.sh` дополнительно проверяет занятость порта до старта uvicorn.
  Типичный сценарий — сервис сам поднялся после перезагрузки и держит базу.
* **Стриминг переотправляется дословно.** Не собирайте события заново из разобранного
  JSON — потеряются поля, о которых прокси не знает, и клиентские SDK начнут спотыкаться.
* **`accept-encoding` вырезается специально.** httpx сам распаковывает ответ; если
  пробросить заголовок, клиент получит нечитаемое тело.
* **Лог хранит оригинальный ответ**, без вставленного предупреждения о балансе.
  Порядок в `proxy.handle` (сначала заполнить `entry`, потом менять `raw`) намеренный.
* **Тела обрезаются** до 400 000 символов. При больших ответах база растёт быстро —
  для этого и нужен ретеншен. Встроенные картинки до обрезки выносятся в файлы.
* **В апстрим уходит исходное тело.** `media.extract_request` возвращает изменённую копию
  только для лога; нельзя подменять ею `body` в `proxy.handle`.
* **Суммы стоимости в агрегатах — только `cost`.** `cost_api`/`cost_estimated` — сырьё
  для `recompute_costs`; новые агрегаты должны читать `cost`, иначе разойдутся с режимом.

## Известные шероховатости

* `@app.on_event("startup"/"shutdown")` — устаревший в свежих FastAPI способ; работает,
  но при обновлении стоит перейти на `lifespan`. Риск не теоретический: ровно так же
  «работающая, но устаревшая» сигнатура `TemplateResponse` перестала существовать
  в новой Starlette и положила все страницы.
* Кэш баланса живёт в переменных модуля `proxy` — при нескольких воркерах uvicorn
  они разъедутся, а DuckDB всё равно не даст запустить второй процесс. Сервис
  рассчитан на один воркер.
* Стоимость медиа-задач не считается: прайс не потокенный, см. `docs/API-NOTES.md`.
* Оценка по прайсу не знает цены кэшированных токенов и считает их по полной — у длинных
  диалогов с кэшем она кратно выше цены из API.
* Внешние ссылки на медиа не скачиваются и со временем истекают.
* Из потоковых ответов картинки не извлекаются: для стрима хранится склеенный текст
  и хвост событий.
* Версии зависимостей не закреплены сверху (`>=`), поэтому на разных машинах ставятся
  разные версии. Ловит это `test_web.py`; при желании стабильности — зафиксируйте
  версии через `pip freeze`.

## Диагностика проблем с доступом

Прокси может быть полностью исправен, а страница не открываться. Порядок проверки —
от сервиса к сети:

```bash
./service.sh status                       # запущен? какой адрес и порт? отвечает ли HTTP
curl --noproxy '*' http://localhost:9090/monitor   # с самой машины
curl --noproxy '*' http://<адрес>:9090/monitor     # с другой машины, минуя прокси
```

Что уже встречалось:

* **Адрес не тот.** `hostname -I` отдаёт первый из нескольких адресов; у машины могут
  быть Wi-Fi, Tailscale, docker-мосты. Локальный `192.168.x.x` работает только внутри
  своей сети — из другой сети с тем же диапазоном он ведёт в никуда.
* **Системный прокси.** `curl` не читает настройки прокси macOS, а браузер читает.
  Если в системе включён прокси (Clash и подобные), браузер отдаёт запрос ему,
  и адрес в обход интернета (Tailscale `100.64.0.0/10`, локальная сеть) не доезжает.
  Лечится исключением в системных настройках сети, а не только правилом в Clash:
  проверено, что `IP-CIDR,100.0.0.0/8,DIRECT` может не срабатывать даже для голого IP.
* **Порт занят.** `./run.sh` и `service.sh install` предупредят; вручную —
  `lsof -nP -iTCP:<порт> -sTCP:LISTEN` или `ss -lntp`.
