# AI Monitoring Proxy

Локальный прокси к ИИ-API (по умолчанию — SpeShu.AI): подставляет API-ключ, пишет все запросы
и ответы в DuckDB и показывает веб-интерфейс с логом, балансом, статистикой по моделям
и документацией.

```
клиент ──► http://localhost:8787/v1/... ──► прокси (ключ + лог) ──► base_url/v1/...
                                              │
                                              └──► DuckDB ──► /monitor /balance /models
```

## Быстрый старт: установка как сервиса

Прокси ставится сервисом — стартует сам, поднимается после падения и переживает
перезагрузку. Зависимости скрипт установит сам.

```bash
./service.sh install                            # только localhost
./service.sh install --host 0.0.0.0 --port 9000 # с доступом из локальной сети
```

Дальше откройте <http://localhost:8787/> — если прокси ещё не настроен,
вас перенаправит на `/settings`, где нужно указать API-ключ.

| Команда                  | Что делает                                       |
| ------------------------ | ------------------------------------------------ |
| `./service.sh status`    | Установлен, загружен, кто занял порт, отвечает ли |
| `./service.sh start`     | Запустить                                        |
| `./service.sh stop`      | Остановить                                       |
| `./service.sh restart`   | Перезапустить (например, после `git pull`)        |
| `./service.sh logs`      | Хвост журнала                                    |
| `./service.sh uninstall` | Снять сервис; `data/` не трогается                |

На macOS ставится LaunchAgent `~/Library/LaunchAgents/com.aipuroxy.proxy.plist`
и журнал пишется в `data/logs/service.log` и `service.err.log`.
На Linux — юнит `~/.config/systemd/user/ai-puroxy.service`, а журнал идёт в journald
(`./service.sh logs` показывает именно его; файлы в `data/logs/` там не заполняются).

Чтобы на Linux сервис стартовал без входа в систему: `loginctl enable-linger $USER`.

Настройки берутся из `data/config.json`, как и при обычном запуске, — страница
`/settings` продолжает работать.

**Адрес и порт задаются при установке**, а не в `/settings`: они попадают в plist
(или юнит systemd). Чтобы их изменить, повторите установку с новыми значениями —
скрипт сам остановит прежний экземпляр:

```bash
./service.sh install --host 0.0.0.0        # слушать все интерфейсы
./service.sh install --host 127.0.0.1      # вернуть только localhost
./service.sh install --host 0.0.0.0 --port 9000
```

Проверить, что получилось: `./service.sh status` или `lsof -nP -iTCP:8787 -sTCP:LISTEN`
— при `0.0.0.0` в выводе будет `*:8787`, при localhost `127.0.0.1:8787`.

LaunchAgent запускается при входе пользователя, а не при загрузке машины. Если прокси
нужен без входа в систему, потребуется LaunchDaemon в `/Library/LaunchDaemons`
(права root); на Linux — `loginctl enable-linger $USER`.

## Запуск без сервиса

Для разработки и разовых проверок удобнее запускать в переднем плане:

```bash
./install.sh      # один раз: .venv и зависимости
./run.sh          # порт 8787 по умолчанию
./run.sh 9000     # другой порт
```

Совсем вручную:

```bash
python3 -m venv .venv && ./.venv/bin/pip install -r requirements.txt
./.venv/bin/python -m uvicorn app.main:app --port 8787
```

Порт должен быть свободен: если сервис уже занял 8787, сначала `./service.sh stop`.

### «Не могу запустить» после перезагрузки

Сервис стартует сам при входе в систему, поэтому после перезагрузки прокси
обычно **уже работает** — проверьте `./service.sh status` и откройте
<http://localhost:8787/monitor>.

Ручной `./run.sh` в этот момент не запустится: база DuckDB допускает только одного
писателя, и второй экземпляр её не откроет. Скрипты об этом предупредят явно.
Нужен ручной запуск — сначала `./service.sh stop`.

## Доступ из локальной сети

По умолчанию прокси слушает только `127.0.0.1`, поэтому с других устройств он
не открывается — это не сбой, а умышленное ограничение. Чтобы разрешить доступ:

```bash
./service.sh install --host 0.0.0.0   # сервисом
AI_PROXY_HOST=0.0.0.0 ./run.sh        # в переднем плане
```

Оба варианта подскажут адрес вида `http://192.168.1.25:8787/monitor`.

> **Аутентификации у интерфейса нет.** Открыв порт наружу, вы даёте любому, кто до него
> дотянется, тратить ваш баланс через прокси и увидеть API-ключ на странице `/settings`.
> Делайте это только в доверенной сети. Безопаснее оставить `127.0.0.1` и пробросить порт
> по SSH: `ssh -L 8787:localhost:8787 пользователь@машина`.

На macOS при первом запуске с внешним адресом системный фаервол может спросить
разрешение на приём входящих подключений.

## Использование

Замените базовый URL в своём клиенте — ключ подставит прокси:

```bash
curl http://localhost:8787/v1/models
curl http://localhost:8787/v1/balance

curl -X POST http://localhost:8787/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"google/gemma-3n-e4b-it","messages":[{"role":"user","content":"Привет"}]}'
```

Работают оба префикса — `/v1/…` и `/api/v1/…`, поэтому в SDK достаточно заменить
`https://speshu.ai/api` на `http://localhost:8787/api` (ключ можно указать любой, он игнорируется).

Проксируются все эндпоинты из документации, включая потоковые (`stream: true`) — SSE идёт
клиенту без буферизации, а прокси попутно собирает из чанков токены и стоимость:

| Метод  | Путь                              |
| ------ | --------------------------------- |
| GET    | `/v1/models`                      |
| POST   | `/v1/chat/completions`            |
| POST   | `/v1/messages`                    |
| GET    | `/v1/media/models`                |
| POST   | `/v1/async/media/tasks`           |
| GET    | `/v1/async/media/tasks`           |
| GET    | `/v1/async/media/tasks/{task_id}` |
| POST   | `/v1/media/sessions`              |
| GET    | `/v1/balance`                     |

Маршрут — сквозной (`/v1/{path}`), так что новые эндпоинты API заработают без правок кода.

## Страницы

| Адрес       | Что показывает                                                                       |
| ----------- | ------------------------------------------------------------------------------------ |
| `/`         | Редирект на `/monitor`, а если прокси не настроен — на `/settings`                    |
| `/monitor`  | Лог запросов: что спросили, что модель думала и какие инструменты дёрнула; фильтры и линейный график по дням сверху |
| `/balance`  | Текущий баланс, календарь трат по дням (как на сайтах с авиабилетами) и детализация по моделям за выбранный день |
| `/models`   | Рейтинг моделей по количеству запросов; клик по имени открывает `/monitor` с фильтром |
| `/settings` | Форма конфигурации                                                                    |
| `/docs`     | Документация API с подстановкой домена из настроек                                     |

## Настройки (`/settings`)

| Параметр                    | По умолчанию            | Описание                                                              |
| --------------------------- | ----------------------- | --------------------------------------------------------------------- |
| API-ключ ИИ-API            | —                       | Подставляется в `Authorization: Bearer …`. Пустое поле = не менять    |
| Base URL ИИ-API            | `https://speshu.ai/api` | Куда проксировать; пути добавляются как `/v1/…`                        |
| Количество хранимых дней    | `0`                     | Записи старше N дней удаляются; `0` — хранить всё                      |
| Порог остатка баланса       | `0`                     | Ниже порога в начало текстовых ответов добавляется предупреждение; `0` — выключено |
| Домен сайта для документации| `localhost`             | Подставляется вместо `speshu.ai` в примерах на `/docs`                 |
| Интервал опроса баланса     | `300` сек               | Как часто прокси сам запрашивает `/v1/balance`                         |

Конфигурация лежит в `data/config.json`, база — в `data/proxy.duckdb`.
**Ключ хранится в открытом виде**, поэтому не коммитьте `data/`.

Первичную настройку можно задать переменными окружения `AI_PROXY_API_KEY` и `AI_PROXY_BASE_URL`,
каталог данных — через `AI_PROXY_DATA_DIR`.

### Предупреждение о низком балансе

Когда баланс опускается ниже порога, прокси дописывает в начало текстового ответа строку вида

```
⚠️ Низкий баланс ИИ-API: 42.10 ₽ (порог 100.00 ₽). Пополните счёт, чтобы запросы не начали отклоняться.
```

Работает для `/v1/chat/completions` (обычные ответы и SSE — отдельным первым чанком)
и для `/v1/messages` (обычные ответы и `content_block_delta` в стриме). Ответы без текста
(каталоги моделей, статусы задач, ошибки) не изменяются.

## Что видно в мониторинге

Прокси разбирает тела запросов и ответов, поэтому в логе видно не только «ответ 660 Б»:

* **строка списка** — запрос (`→`), **о чём модель думала** (`💭`, курсивом) и ответ (`←`),
  плюс значки: 🔧 вызванные инструменты, 💭 токены рассуждений, 🖼 изображения,
  ⚡ токены из кэша, `stream` и причина завершения, если она не обычная
  (`tool_calls`, `length`);
* **карточка запроса** (клик по строке) — вкладка «Диалог» с системным промптом,
  сообщениями, **полным текстом рассуждений**, вызовами инструментов и их аргументами;
  вкладка «Сырой JSON» — как было раньше. Длинные промпты и старые сообщения свёрнуты,
  чтобы рассуждения и ответ не уезжали вниз;
* **фильтры** — «с инструментами», «с рассуждениями», «с изображениями», «потоковые»;
* **прямая ссылка** на запрос: `/monitor?request=146`.

Рассуждения берутся из `message.reasoning` (для стримов склеиваются из `delta.reasoning`),
вызовы инструментов — из `tool_calls`, в потоке аргументы собираются из фрагментов.
Записи, сделанные до появления этих полей, разбираются автоматически при первом запуске.

## Как считается стоимость

1. Из ответа API, если он её вернул — `usage.cost.total_cost` (актуальный формат)
   или `usage.cost_rub` (формат из документации). В интерфейсе — без пометки.
2. Иначе — оценка по прайсу из `GET /v1/models` (цены за 1M токенов), который прокси кэширует
   при каждом проксировании этого эндпоинта. Такие значения помечены `*` и подписью «оценка»:
   так считается, например, `/v1/messages`, где API стоимость не возвращает.
3. Медиа-задачи стоимости в ответе не содержат и прайс у них не потокенный, поэтому в сумму
   по логу они не попадают.

Календарь и разбивка по моделям строятся по логу запросов. Параллельно прокси снимает
снимки `/v1/balance`, поэтому в подсказке дня видно баланс на конец дня, а в детализации —
фактическое изменение баланса за день. Разница между «по логу» и «по балансу» — это как раз
траты, которые API не тарифицирует в ответе (медиа-задачи), и пополнения счёта.

## Тесты

```bash
./.venv/bin/python tests/test_core.py   # логика: usage, баланс, ретеншен, документация
./.venv/bin/python tests/test_web.py    # HTTP: все страницы, /docs, /_api/*
```

Первый проверяет разбор обоих форматов usage и баланса, оценку стоимости по прайсу,
ретеншен, замену домена в документации, вставку предупреждения и нормализацию путей.
Второй поднимает приложение через `TestClient` и рендерит каждую страницу — он ловит
поломки шаблонов и несовместимость с новыми версиями FastAPI/Starlette
(`DeprecationWarning` там возведён в ошибку).

Внешняя сеть не требуется — тесты работают на временной базе.

## Структура

```
app/
  main.py      маршруты: страницы, /_api/* для интерфейса, сквозной прокси /v1/*
  proxy.py     проксирование, стриминг, предупреждение о балансе
  db.py        DuckDB: лог запросов, снимки баланса, кэш цен, ретеншен
  usage.py     разбор usage/стоимости/баланса, оценка по прайсу
  stats.py     агрегаты для интерфейса
  config.py    конфигурация в data/config.json
  docsrc.py    рендер документации с заменой домена
  docs/        исходные .md документации API
  templates/   Jinja2-шаблоны страниц
  static/      CSS и JS (без внешних зависимостей и CDN)
tests/
```
